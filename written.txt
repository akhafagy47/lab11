2a. With batching (main.cpp, SpriteManager::drawGL) the FPS converged to about 31 FPS, and the
unbatched sf::Sprite version (main_nobatch.cpp) also converged to about 31 FPS (Debug build, macOS);
in a Release build both rose to about 39.5 FPS, again tied. Batching cuts the frame from ~10,000 draw
calls to a single glDrawArrays, but since both versions ran at the same rate, draw-call overhead
wasn't the bottleneck on this machine; the frame time is most likely dominated by work both programs
share, such as the CPU-side per-particle update (recomputing 10,000 sphere positions with trig and
updating textures every frame).

2b. Give each sprite a depth value (e.g., store it as a third vertex position component or as an
extra component of its transform) and write it to gl_Position.z in the vertex shader instead of 0.
Then enable the depth test (glEnable(GL_DEPTH_TEST) with glDepthFunc(GL_LESS)) and clear the depth
buffer each frame (we already request a 24-bit depth buffer and clear GL_DEPTH_BUFFER_BIT), so the
rasterizer interpolates depth per fragment and automatically discards fragments hidden behind closer
ones, regardless of draw order. (Semi-transparent sprites would still need to be sorted back-to-front
or have fully transparent fragments discarded, since the depth test doesn't blend.)
